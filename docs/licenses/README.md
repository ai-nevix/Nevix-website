# Licence Inventory

> Specification §11: *"Maintain an inventory of package versions and licences and review them for
> commercial compatibility. 'Open source' should be verified at the exact version used, not
> assumed."*
>
> Instruction §5, §14.

## Files

| File | Contents | Generated by |
| --- | --- | --- |
| [`npm-dependencies.md`](./npm-dependencies.md) | Every npm package with its resolved version and licence | `npm run licenses:inventory` |
| [`python-dependencies.md`](./python-dependencies.md) | Every Python package with its licence | `scripts/generate-python-licenses.sh` |
| [`infrastructure.md`](./infrastructure.md) | Container images and infrastructure components | Maintained by hand |

The npm inventory reads the versions **actually resolved in `node_modules`**, not the ranges
declared in `package.json`. That distinction is the whole point of the specification's wording: a
range can resolve to a version whose licence has changed.

## Regenerating

```bash
npm run licenses:inventory                    # write the report
node scripts/generate-license-inventory.mjs --check   # CI gate
```

`--check` fails the build on any licence the classifier does not recognise. That is deliberate: a
dependency that relicenses should become a decision, not a silent change. It runs in CI.

## Classification

**Permissive — no obligations beyond attribution**
MIT, MIT-0, ISC, BSD-2-Clause, BSD-3-Clause, 0BSD, Apache-2.0, Unlicense, CC0-1.0, BlueOak-1.0.0,
Python-2.0, WTFPL, Zlib.

**Copyleft — permitted, with the reasoning recorded**
Each is documented individually in the generated report. Current entries:

| Licence | Packages | Why it is acceptable here |
| --- | --- | --- |
| MPL-2.0 | `axe-core`, `@axe-core/playwright`, `lightningcss` | File-level copyleft. We do not modify these files; obligations attach only to modifications. `axe-core` is a dev dependency and never ships. |
| Apache-2.0 AND LGPL-3.0-or-later | `@img/sharp-win32-x64` | LGPL is reached through the libvips library bundled with sharp. Dynamic linking inside a container is the standard accepted use, and libvips is not modified. This is also a **platform-specific optional dependency** — it is not installed in the Linux production image. |
| CC-BY-4.0 | `caniuse-lite` | Attribution-only, applies to browser-support *data* consumed at build time. Nothing ships. |
| AGPL-3.0 | Grafana, Loki (container images, not npm) | Operated internally only. Not offered as a service to third parties, which is what triggers AGPL's network clause. See the caveat below. |

**Unrecognised — blocks the build**
Anything else. Verify manually, then add it to `PERMISSIVE` or `REVIEW_REQUIRED` in
`scripts/generate-license-inventory.mjs` with a note explaining the decision.

### On `AND` versus `OR`

The classifier treats these differently, because they mean different things:

- `MIT OR Apache-2.0` — we may choose either, so one permissive alternative is sufficient
- `Apache-2.0 AND LGPL-3.0-or-later` — **both** apply, so the most restrictive term governs

Treating `AND` like `OR` would silently pass a copyleft obligation as permissive. That is the kind
of error a licence inventory exists to prevent, so it is tested by the classifier's structure
rather than left to the reader.

## Caveats worth knowing before they matter

**Grafana and Loki are AGPL-3.0.** Not a problem as internal observability tooling. It *would*
become one if NEVIX embedded Grafana in a client-facing product — AGPL's network clause extends
the copyleft to users who interact with the software over a network. Recorded here so it is a known
boundary rather than a late discovery.

**Strapi Community Edition is MIT, but not everything is in it.** SSO, audit logs, publication
workflows and content-type-level permissions are Enterprise-only. Nothing this site depends on is
behind that line. A future requirement for editorial approval workflows would hit it.

**`UNLICENSED` entries are ours.** The NEVIX workspace packages are marked `UNLICENSED` because
they are proprietary and not published.

## Review cadence

- On every dependency change — automatically, via the CI gate
- Before any production release — read the report, do not just let the gate pass
- On any major version upgrade of a copyleft dependency — re-read its licence, since projects do
  relicense
